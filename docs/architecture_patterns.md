## UI/前端架构模式

关注如何组织用户界面代码，应对复杂交互和状态管理。

---

### MVC（Model-View-Controller）

**分类**：UI/前端架构

**原理**：最经典、最广为人知的架构模式，将应用分为三层：

```
┌─────────┐     ┌─────────┐     ┌─────────┐
│  View   │ ←── │Controller│ ──→ │  Model  │
│  (界面) │     │ (控制器) │     │  (数据) │
└─────────┘     └─────────┘     └─────────┘
```

| 角色 | 职责 | 是否依赖其他层 |
|------|------|----------------|
| **Model** | 数据和业务逻辑，不依赖 UI | 无依赖 |
| **View** | 展示层，渲染界面 | 依赖 Model（读取数据） |
| **Controller** | 接收用户输入，操作 Model，更新 View | 依赖 Model 和 View |

**关键特征**：
- Controller 是用户请求的入口
- View 可以直接从 Model 读取数据（被动更新）
- 适合简单到中等复杂度的应用

**适用场景**：
- Web 框架（Django MTV、Ruby on Rails）
- 传统桌面应用
- 不需要复杂状态管理的应用

**检测依据**：
- 同时存在包含 `Model`、`View`、`Controller`（或 `Ctrl`）关键词的类/模块
- 目录结构中存在对应分层

**常见误报**：任何同时包含这三个词的代码都可能被误判，需结合目录结构确认。

---

### MVP（Model-View-Presenter）

**分类**：UI/前端架构

**原理**：MVC 的演进版本，解决 View 和 Model 耦合过紧的问题：

```
用户操作 → View (接口) → Presenter ←→ Model
                    ↓
                View (实现)
```

| 角色 | 职责 |
|------|------|
| **Model** | 数据层 |
| **View** | 界面层（通常定义为接口/协议，很薄） |
| **Presenter** | 同时持有 View 和 Model，负责所有业务逻辑和界面更新 |

**与 MVC 的核心区别**：
- View 和 Model **完全解耦**（View 不直接读取 Model）
- Presenter 主动更新 View（通过接口调用）
- View 很薄，几乎不含业务逻辑

**适用场景**：
- 需要高可测试性的应用（Presenter 可以脱离 View 单独测试）
- Android 开发（早期官方推荐架构）

**检测依据**：
- 存在 `Presenter` 类
- Presenter 同时引用 View 接口和 Model
- View 定义为接口/协议（如 `interface View { ... }`）

---

### MVVM（Model-View-ViewModel）

**分类**：UI/前端架构

**原理**：通过**数据绑定**连接 View 和 ViewModel，是 MVP 的进一步演进：

```
View ←─── (数据绑定) ───→ ViewModel ←──→ Model
```

| 角色 | 职责 |
|------|------|
| **Model** | 数据层 |
| **View** | 界面层（声明式绑定，很薄） |
| **ViewModel** | 暴露数据和命令，View 通过绑定自动更新 |

**关键特征**：
- ViewModel 不引用 View（通过绑定机制解耦）
- View 的更新是**自动的**（数据变化时界面自动刷新）
- 通常需要框架支持（如 WPF 的 `{Binding}`、Vue 的响应式系统）

**适用场景**：
- WPF / UWP（Windows 桌面）
- Vue / React + 状态管理（部分理念）
- 需要复杂界面交互的应用

**检测依据**：
- 存在 `ViewModel` 类
- 检测到数据绑定相关关键词（`bind`、`observe`、`notify`、`reactive`）
- ViewModel 暴露的属性/命令被 View "监听"

**注意**：纯 Python 项目中 MVVM 较少见（除非使用 PyQt/PySide 的数据绑定）。

---

### MVI（Model-View-Intent）

**分类**：UI/前端架构

**原理**：强调**单向数据流**，数据流动路径清晰可追踪：

```
用户操作
    ↓
[Intent]  (封装用户意图）
    ↓
[Model]   (处理意图，更新状态）
    ↓
[State]   (新的应用状态）
    ↓
[View]    (根据 State 渲染界面）
    ↓
（产生新的 Intent，形成闭环）
```

**关键特征**：
- **单向数据流**：数据只朝一个方向流动（Intent → Model → State → View）
- **状态不可变**：State 是不可变数据，每次更新都产生新 State
- **易于调试**：任何时刻的应用状态都可以序列化和回放

**适用场景**：
- 响应式 UI（Flutter + Bloc）
- React + Redux（前端）
- 需要可预测状态管理的应用

**检测依据**：
- 同时存在 `Intent` 和 `State` 相关的类/类型定义
- 检测到单向数据流的特征（如 `dispatch(intent)` → `reduce(state, intent)` → `render(state)`）

**误报提示**：当前检测器只要检测到 `Intent` + `State` 关键词就会判定为 MVI，可能存在误报。需结合代码实际数据流确认。

---

### MVU（Model-View-Update）

**分类**：UI/前端架构

**原理**：与 MVI 理念相似，但来自**函数式编程**传统（Elm 语言首创）：

```
[Model]  (不可变状态）
    ↓
[View]    (纯函数：Model → View）
    ↓
用户操作产生 [Message]
    ↓
[Update]  (纯函数：Message + Model → 新 Model）
    ↓
（循环）
```

| 概念 | 说明 |
|--------|------|
| **Model** | 应用状态（不可变数据） |
| **View** | 纯函数，根据 Model 渲染界面 |
| **Update** | 纯函数，接收 Message 和当前 Model，返回新 Model |
| **Message** | 用户操作或事件的枚举类型 |

**关键特征**：
- 所有状态更新都通过 `Update` 纯函数完成
- `Update` 函数签名通常为：`update(msg: Message, model: Model) -> Model`
- 易于测试（纯函数，无副作用）

**适用场景**：
- Elm 语言（原创）
- React + Redux（类似理念）
- F# + Fable（Web 开发）
- 某些 Python 函数式 GUI 框架

**检测依据**：
- 存在 `update()` 纯函数
- 存在 `Message` 或 `Msg` 类型定义（枚举）
- `View` 是纯函数（接收 Model，返回界面描述）

---

### VIPER（View-Interactor-Presenter-Entity-Router）

**分类**：UI/前端架构

**原理**：iOS 开发中最常用的架构，将职责划分得最细：

```
┌────────────────────────────────────────┐
│                 VIPER                  │
│  ┌──────┐  ┌────────┐  ┌──────┐  │
│  │ View  │←─│Presenter│─→│ Router│  │
│  └──────┘  └────────┘  └──────┘  │
│                ↓                     │
│         ┌────────┐  ┌────────┐    │
│         │Interactor  │  ┌──────┐    │
│         └────────┘  └────────┘    │
└────────────────────────────────────────┘
```

| 角色 | 职责 | 是否持有其他角色 |
|------|------|----------------|
| **View** | 展示界面，转发用户操作 | 持有 Presenter（弱引用） |
| **Interactor** | 业务逻辑层（类似 Use Case） | 不持有任何 VIPER 角色 |
| **Presenter** | View 和 Interactor 之间的桥梁，格式化数据 | 持有 View（接口）和 Interactor |
| **Entity** | 数据模型（纯数据结构） | 无依赖 |
| **Router** | 页面导航和流程控制 | 持有 View |

**关键特征**：
- 每个功能模块都完整包含这 5 个组件
- 极高的**可测试性**（每个组件都可以独立单元测试）
- 极高的**模块化**（方便多人协作）
- 代价是**复杂度高**（小功能也需要创建 5 个文件）

**适用场景**：
- iOS 开发（原生推荐架构）
- 需要高可测试性的移动应用
- 大型团队协同开发

**检测依据**：
- 目录/文件中同时存在 View、Interactor、Presenter、Entity、Router 相关的类
- 通常按功能模块组织目录（每个模块一个子目录）

**误报提示**：Python 项目中使用 VIPER 的情况较少，如果检测到可能是误报。

---

### MVVM-C（Model-View-ViewModel-Coordinator）

**分类**：UI/前端架构（MVVM 的变体）

**原理**：在 MVVM 基础上引入 `Coordinator` 层，专门负责管理视图间的导航：

```
[MVVM]  (原有结构）
    +
[Coordinator]  (导航层，管理页面跳转流程）
```

**问题背景**：
- 在复杂应用中，ViewModel 会变得臃肿（既要管理数据绑定，又要管理页面跳转）
- ViewModel 之间可能相互引用，产生耦合

**解决方案**：
- 将**导航逻辑**从 ViewModel 中抽取到独立的 Coordinator
- ViewModel 只负责数据和绑定，不关心"接下来跳转到哪里"
- Coordinator 负责"下一步是什么"，ViewModel 负责"当前页面怎么展示"

**适用场景**：
- iOS 开发（Swift + Coordinators 模式）
- 需要复杂页面流转的应用

**检测依据**：
- 存在 `Coordinator` 类
- Coordinator 负责管理多个 ViewModel 之间的跳转关系

---

## 系统架构模式

关注宏观的系统结构，决定软件的整体骨架。

---

### 分层架构（Layered Architecture）

**分类**：系统架构

**原理**：最经典、最直观的架构模式，将系统按职责划分为多个层：

```
┌────────────────────────────┐
│   展示层 (Presentation)     │  ← 第 1 层
├────────────────────────────┤
│   应用层 (Application)      │  ← 第 2 层
├────────────────────────────┤
│   领域层 (Domain)           │  ← 第 3 层
├────────────────────────────┤
│   基础设施层 (Infrastructure) │  ← 第 4 层
└────────────────────────────┘
```

**依赖规则**（关键！）：
- **上层依赖下层**，下层不知道上层的存在
- 第 2 层 → 第 3 层 → 第 4 层（依赖方向单一）
- 禁止「下层反向依赖上层」（否则分层失去意义）

**各层职责**：

| 层 | 职责 | 示例 |
|----|------|------|
| 展示层 | 处理用户请求，返回响应 | HTTP Controller、CLI 解析 |
| 应用层 | 用例编排，事务边界 | `OrderService.placeOrder()` |
| 领域层 | 核心业务逻辑和不变量 | `Order` 聚合、`calculateTotal()` |
| 基础设施层 | 技术实现细节 | ORM、数据库、消息队列 |

**优势**：
- 简单直观，易于理解
- 关注点分离明确

**劣势**：
- 「雪崩式修改」：底层变更可能层层向上传播
- 性能问题：跨层调用增加延迟

**适用场景**：
- 小型到中型项目（< 5 人年）
- 业务规则相对简单的系统
- 原型开发

**检测依据**：
- 目录结构中存在分层（如 `presentation/`、`service/`、`domain/`、`infrastructure/`）
- 依赖方向符合「上层 → 下层」规则

---

### 六边形架构（Hexagonal Architecture / 端口-适配器）

**分类**：系统架构

**原理**：由 Alistair Cockburn 于 2005 年提出，核心隐喻为「应用核心 + 端口 + 适配器」：

```
           ┌───────────────┐
           │   应用核心      │
           │  (业务逻辑）    │
           └──────┬────────┘
                  ↑↓ (端口）
    ┌─────────────┼─────────────┐
    │             │             │
┌───┴───┐  ┌───┴───┐  ┌──┴────┐
│ 适配器  │  │ 适配器  │  │ 适配器  │
│(HTTP)  │  │ (CLI)   │  │(定时任务)│
└────────┘  └────────┘  └────────┘
      ↑ (主适配器：驱动端口）
                 
┌───────────────┐
│   应用核心      │
│  (业务逻辑）    │
└──────┬────────┘
         ↑↓ (端口）
    ┌────┴────┐
    │  适配器   │
    │ (MySQL)  │
    └─────────┘
      ↑ (从适配器：被驱动端口）
```

**两个关键概念**：

| 概念 | 说明 | 示例 |
|--------|------|------|
| **驱动端口**（Primary Port） | 应用核心对外暴露的能力，由外部主动调用 | `OrderUseCase`（应用服务接口） |
| **被驱动端口**（Driven Port） | 应用核心需要外部提供的能力，由核心反向调用 | `OrderRepository`（仓储接口） |
| **主适配器** | 将外部请求翻译为驱动端口调用 | `OrderHttpController` → 调用 `OrderUseCase` |
| **从适配器** | 将被驱动端口调用翻译为外部技术实现 | `OrderMySqlRepository` → 实现 `OrderRepository` |

**核心价值**：
- 应用核心**完全独立于技术细节**（换数据库、换 Web 框架都不需要改核心代码）
- 支持**单元测试脱离框架**单独运行
- 符合**依赖倒置原则**（DIP）

**与分层架构的关系**：
- 六边形架构可以理解为「分层架构的旋转版」
- 核心思想一致：领域居中，依赖向内
- 六边形更强调「对称化」（入口和出口都用端口+适配器处理）

**适用场景**：
- 需要长期维护的业务系统
- 需要替换技术栈的项目
- 领域逻辑复杂的系统

**检测依据**：
- 存在「端口」（接口定义）和「适配器」（接口实现）的组织结构
- 应用核心不依赖任何外部框架/数据库
- 目录结构中存在 `port/` 或 `adapter/` 关键词

---

### 微服务架构（Microservices）

**分类**：系统架构

**原理**：将单体应用拆分为多个**独立部署**的服务，每个服务围绕业务能力构建：

```
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 订单服务  │  │ 用户服务  │  │ 支付服务  │
│ (独立进程)│  │ (独立进程)│  │ (独立进程)│
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │               │               │
     └───────────────┼───────────────┘
                     │
              ┌──────┴──────┐
              │   消息总线      │
              │ (Kafka/RabbitMQ) │
              └─────────────┘
```

**关键特征**：
- 每个服务**独立部署**、**独立扩展**
- 服务间通过**网络调用**（HTTP/gRPC）或**消息队列**通信
- 数据**去中心化**（每个服务有自己的数据库）

**优势**：
- 技术栈灵活（不同服务可以用不同语言/框架）
- 故障隔离（一个服务挂了不影响其他服务）
- 扩展性强（只需要扩展热点服务）

**劣势**：
- **分布式系统的复杂性**（网络延迟、分布式事务、服务发现）
- 运维成本高（需要 CI/CD、监控、日志聚合）
- 数据一致性难保证（需要用最终一致性）

**适用场景**：
- 大型系统（> 10 人团队）
- 需要独立扩展不同业务模块
- 需要高可用性和容错性

**检测依据**：
- 目录结构中存在多个「服务目录」（如 `order-service/`、`user-service/`）
- 每个服务目录都是独立可运行的（有自己的 `main.py` 或 `app.py`）
- 服务间通过 HTTP/gRPC 调用（代码中可检测到）

**注意**：Python 项目中使用微服务架构的情况相对较少（更常见的是 Java/Go），检测器可能会误判。

---

### 事件驱动架构（Event-Driven Architecture）

**分类**：系统架构

**原理**：系统组件通过**事件**进行异步通信，组件之间松耦合：

```
┌──────────┐   发布事件    ┌──────────────┐
│ 组件 A   │ ──────────→  │  事件总线     │
└──────────┘              │ (Event Bus)  │
                         └──────┬───────┘
                                │ 分发事件
                    ┌───────────┼───────────┐
                    ↓           ↓           ↓
             ┌──────────┐ ┌──────────┐ ┌──────────┐
             │ 组件 B   │ │ 组件 C   │ │ 组件 D   │
             │ (订阅者) │ │ (订阅者) │ │ (订阅者) │
             └──────────┘ └──────────┘ └──────────┘
```

**关键概念**：

| 概念 | 说明 |
|--------|------|
| **事件** | 系统中已发生的事实（用过去式命名，如 `OrderPlaced`） |
| **发布者** | 产生事件并发布到事件总线的组件 |
| **订阅者** | 监听特定事件并做出反应的组件 |
| **事件总线** | 负责接收事件并分发给所有订阅者的中间件 |

**两种常见变体**：

1. **事件通知**（Event Notification）：事件只包含「发生了什么」，订阅者需要主动查询详情
2. **事件携带状态转移**（Event-Carried State Transfer）：事件包含完整状态，订阅者不需要额外查询

**优势**：
- 组件之间**松耦合**（发布者不知道有哪些订阅者）
- **高扩展性**（新增订阅者不需要修改发布者）
- 天然支持**异步处理**

**劣势**：
- 流程**难以追踪**（一个操作可能触发多个异步事件，调试困难）
- **事件幂等性**需要仔细设计（同一个事件可能被重复处理）
- 需要**事件总线中间件**（如 Kafka、RabbitMQ）

**适用场景**：
- 需要高响应性的系统
- 组件之间需要松耦合
- 需要事件审计和回放

**检测依据**：
- 代码中大量使用事件相关关键词：`event`、`subscribe`、`publish`、`emit`、`on_`、`listener`、`handler`、`dispatch`
- 存在事件总线/消息队列的使用（如 `kafka`、`rabbitmq`、`redis pub/sub`）

---

### 微内核架构（Microkernel Architecture / 插件架构）

**分类**：系统架构

**原理**：由一个仅包含最小核心功能的内核和多个独立的插件模块组成：

```
┌─────────────────────────────────┐
│           应用                 │
│  ┌──────────┐  ┌──────────┐ │
│  │  插件 A  │  │  插件 B  │ │
│  └──────────┘  └──────────┘ │
│  ┌──────────┐  ┌──────────┐ │
│  │  插件 C  │  │  插件 D  │ │
│  └──────────┘  └──────────┘ │
│           ↓                   │
│  ┌────────────────────────┐  │
│  │     核心内核 (Microkernel) │  │
│  │  (最小核心功能）          │  │
│  └────────────────────────┘  │
└─────────────────────────────────┘
```

**关键特征**：
- **内核**只提供最基础的功能（如插件加载、生命周期管理）
- **插件**可以灵活「插拔」来扩展系统功能
- 插件之间通常不直接依赖（都依赖内核提供的接口）

**优势**：
- 极高的**可扩展性**（新增功能 = 新增插件）
- 核心稳定（内核代码很少需要修改）
- 插件可以**独立开发和部署**

**劣势**：
- 内核接口设计需要非常谨慎（一旦确定很难修改）
- 插件之间的协作可能需要内核提供额外的协调机制

**适用场景**：
- 需要高度可定制和扩展的应用（如 IDE、文本编辑器）
- 产品线的核心平台（各客户可以开发自己的插件）
- 需要支持第三方扩展的系统

**检测依据**：
- 存在「插件目录」（如 `plugins/`、`extensions/`、`addons/`）
- 内核提供插件接口/抽象类，插件实现这些接口
- 代码中检测到动态加载插件的逻辑（`importlib.import_module`、`pkgutil` 等）

## 业务架构模式

为解决特定业务领域的复杂问题而设计。

---

### CQRS（Command Query Responsibility Segregation）

**分类**：业务架构

**原理**：将**写入操作**（Command）和**读取操作**（Query）在模型和数据库层面完全分离：

```
写入侧                          读取侧
┌────────────┐                 ┌────────────┐
│   Command  │                 │    Query   │
│  (写入请求) │                 │  (查询请求) │
└─────┬──────┘                 └─────┬──────┘
      ↓                               ↓
┌────────────┐                 ┌────────────┐
│ Write Model │                 │  Read Model│
│ (聚合建模)  │                 │ (扁平化视图) │
└─────┬──────┘                 └─────┬──────┘
      ↓                               ↓
┌────────────┐                 ┌────────────┐
│  Write DB  │ ←─── (同步) ───→ │   Read DB  │
└────────────┘                 └────────────┘
```

**背景问题**：
在传统 CRUD 同模型中，写入逻辑（需要保证不变量、事务一致性）和查询需求（需要多表 JOIN、扁平化 DTO）经常产生冲突。

**CQRS 的解决方案**：
- **写侧**：围绕聚合建模，聚焦业务规则、不变量、状态迁移
- **读侧**：面向查询场景设计，预计算好需要的扁平化数据结构
- **同步方式**：写侧发布领域事件，读侧通过事件投影（Projection）更新

**重要澄清**：
- CQRS **不等于**「读写必须分库」（可以同库不同模型）
- CQRS **不要求**所有接口都拆分 Command 和 Query（只在复杂场景使用）

**适用场景**：
- 写入逻辑复杂、查询场景多样的系统
- 读写负载差异很大的系统（如电商：写少读多）
- 需要独立扩展读能力的系统

**不适用场景**：
- 简单的 CRUD 场景（强行使用会增加复杂度）

**检测依据**：
- 存在 `Command` / `Query` 分开的类和接口
- 写模型和读模型是不同类型（写侧用聚合，读侧用 DTO/View）
- 代码中检测到事件投影/同步逻辑

---

### 事件溯源（Event Sourcing）

**分类**：业务架构

**原理**：不保存对象的**当前状态**，而是保存所有**状态变更事件**，通过「重放事件」获取当前状态：

```
传统方式：
┌─────────┐     ┌─────────┐
│  Order  │ ──→ │ 数据库  │  (保存当前状态）
│ (状态)  │     │(OrderRecord)│
└─────────┘     └─────────┘

事件溯源方式：
┌─────────┐     ┌─────────┐
│  Order  │ ──→ │ 事件存储  │  (保存所有事件）
│ (状态)  │     │          │
└─────────┘     │ - OrderCreated  │
                 │ - ItemAdded     │
                 │ - OrderPaid    │
                 │ - OrderShipped │
                 └─────────┘
                              ↓ (重放）
                       ┌──────────────┐
                       │   当前状态    │
                       │ (重放得到）   │
                       └──────────────┘
```

**关键概念**：

| 概念 | 说明 |
|--------|------|
| **事件** | 已发生的事实，用过去式命名（`OrderCreated`、`PaymentReceived`） |
| **事件存储** | 只追加写入（append-only）的存储，保证事件顺序 |
| **重放**（Replay） | 从事件存储读取所有事件，依次应用，得到当前状态 |
| **快照**（Snapshot） | 定期保存状态快照，避免每次都从头重放全部事件 |

**优势**：
- **完整审计能力**：可追溯状态变化的全链路（「这个订单为什么是这个值？」可以直接查事件）
- **支持时间回放**：可以重建任意历史时刻的状态（用于排障、对账、监管审计）
- **天然契合事件驱动**：领域事件同时作为持久化事实

**劣势**：
- **事件版本演进复杂**：已发布的事件不能随意修改结构（需要版本迁移）
- **查询需要额外投影**：否则每次查询都要重放事件（成本极高）
- **学习曲线陡峭**：需要掌握事件建模、幂等、重放、快照等工程能力

**适用场景**：
- 审计要求高的系统（金融、交易、账务）
- 状态变化复杂、需要历史回放的核心域
- 事件驱动架构的自然补充

**不适用场景**：
- 普通后台管理
- 简单 CRUD 场景

**检测依据**：
- 存在「事件存储」相关代码（`EventStore`、`append`、`load_events`）
- 聚合的 `load` 方法通过「重放事件」重建状态（而非从数据库读取当前状态）
- 事件类名使用过去式（`Created`、`Updated`、`Deleted`）

---

### DDD（Domain-Driven Design / 领域驱动设计）

**分类**：业务架构（实为软件设计方法论）

**原理**：由 Eric Evans 于 2003 年提出，是一套**让代码结构反映业务结构**的方法论。

> ⚠️ DDD 不是一种具体的架构模式，而是一种**设计方法论**。
> 它常与分层架构、六边形架构等结合使用。

**核心三要素**：

| 要素 | 说明 |
|------|------|
| **统一语言**（Ubiquitous Language） | 领域专家、产品、研发共用同一套术语体系，术语直接体现在类名、方法名中 |
| **领域模型**（Domain Model） | 业务规则在代码中的精确投射，封装数据、行为和不变量 |
| **限界上下文**（Bounded Context） | 业务概念的意义边界，允许「同名异义」（如"订单"在电商和 ERP 中含义不同） |

**战略设计**（业务边界划分）：

| 概念 | 说明 |
|--------|------|
| **子域分类** | 核心域（差异化能力，重点投入）、支撑域、通用域（可采购/复用） |
| **限界上下文** | 微服务拆分的核心依据 |
| **上下文映射** | 解决跨上下文协作（共享内核、客户-供应商、防腐层 ACL） |

**战术设计**（业务模型定义）：

| 概念 | 说明 |
|--------|------|
| **实体**（Entity） | 有唯一标识、有生命周期、可变的对象 |
| **值对象**（Value Object） | 无唯一标识、不可变、按属性值判等的对象 |
| **聚合**（Aggregate） | 一组业务不可分割的对象集合，聚合根是唯一对外入口 |
| **领域服务**（Domain Service） | 不属于单个实体/值对象的领域行为载体 |
| **领域事件**（Domain Event） | 领域内已发生、值得通知其他部分的事实 |
| **仓储**（Repository） | 「像访问内存集合一样」持久化/查询聚合的抽象 |
| **工厂**（Factory） | 复杂聚合的创建逻辑封装 |

**检测依据**（较难自动化检测，以下为弱信号）：
- 存在「聚合根」相关的类和注释
- 仓储接口定义在领域层（`Repository` 接口）
- 领域事件的使用（`DomainEvent`、`publish`）
- 目录结构中存在 `domain/`、`entity/`、`value_object/` 等

---

## 检测原理说明

`architecture_detector.py` 使用以下方法进行检测：

### 方法一：AST 分析

使用 Python 内置的 `ast` 模块解析代码，提取：
- 所有类名（`ClassDef`）
- 所有函数名（`FunctionDef`）
- 所有导入语句（`Import`、`ImportFrom`）

### 方法二：关键词匹配

根据各架构的特征关键词进行匹配，例如：

| 架构 | 关键词 |
|------|--------|
| MVC | `Model`、`View`、`Controller`、`Ctrl` |
| MVVM | `ViewModel`、`Bind`、`Observe` |
| MVI | `Intent`、`State`、`reduce` |
| 事件驱动 | `event`、`subscribe`、`publish`、`emit`、`handler` |
| 微内核 | `Plugin`、`Extension`、`load_plugin` |

### 方法三：目录结构分析

检查目录组织是否符合特定架构，例如：

```
# 分层架构
presentation/
service/        (或 application/)
domain/
infrastructure/

# 六边形架构
port/           (端口定义）
adapter/        (适配器实现）

# 微内核
kernel/         (核心内核）
plugins/        (插件目录）
```

### 置信度计算

置信度基于「证据数量」动态调整：

```
置信度 = min(1.0, 证据数量 / 期望数量)
```

- **100%**：明确检测到该模式的特征（证据充足）
- **50-99%**：疑似使用该模式（可能有误报）
- **<50%**：弱信号，建议人工确认

1. 使用 `--arch-detail` 查看具体证据
2. 判断误报原因（关键词误匹配？目录结构巧合？）
3. 在 `architecture_detector.py` 中调整对应模式的检测逻辑
4. 重新运行验证
